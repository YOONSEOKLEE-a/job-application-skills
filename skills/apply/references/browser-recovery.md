# 브라우저 확인창·무반응 복구

검색어: 확인 버튼, 저장하시겠습니까, getJsDialog, alert, confirm, 모달, timeout, filechooser, setFiles, 날짜, 자동완성, 연결 끊김.

현재 도구 문서에서 사용 가능한 API를 확인한다. 과거의 제어 성공은 현재 비활성화된 기능을 사용할 권한이나 대체 코드 실행 근거가 아니다.

## 확인 버튼이 안 눌릴 때

### 1. 먼저 버튼과 창의 종류를 확인한다

- **페이지 안 HTML 모달**: DOM/접근성 트리에 문구와 버튼이 보인다. 현재 모달 영역으로 범위를 좁혀 `확인` 버튼을 찾는다. 배경 페이지의 동명 버튼을 누르지 않는다.
- **브라우저 JavaScript confirm/alert**: 페이지 DOM 바깥에 있고 페이지 실행이나 자동화 클릭의 완료를 막을 수 있다. 제공되는 dialog API로 종류·문구를 읽고 처리한다.
- **네이티브 앱/브라우저 창**: 페이지 스냅샷에는 안 보이지만 실제 화면에 보일 수 있다. 허용된 스크린샷·컴퓨터 제어로 확인한다.
- **비활성화된 일반 버튼**: 필수값, 글자 수, 첨부 완료, 중복확인, 약관 펼쳐보기/열람, blur 후 검증 등을 먼저 확인한다. 활성화 속성을 강제로 바꾸거나 내부 제출 함수를 호출하지 않는다.

`getJsDialog()`가 비어 있어도 HTML 모달이나 실제 표시된 확인창이 없다는 뜻은 아니다. 트리가 빈 heading/button 몇 개만 보여도 현재 스크린샷으로 내용을 확인한다. 입력값이 텍스트 조회에서 비어 보였지만 화면에서는 정상 표시된 사례도 있으므로, 곧바로 덮어쓰지 않는다.

### 2. 클릭 대기와 dialog 처리의 순서 교착을 피한다

`await 저장클릭` 다음에 dialog를 조회하면 클릭이 확인창 처리를 기다리며 멈출 수 있다. **클릭 동작을 시작해 pending으로 두고 같은 탭의 dialog를 처리한 뒤 클릭 완료를 기다리는 방식**으로 실제 저장 성공을 확인했다.

현재 API가 해당 동시 처리를 지원할 때만 다음 원리로 구현한다. 이는 실행용 코드나 존재가 보장된 API 이름이 아니다.

```text
현재 화면에서 저장 버튼과 예상되는 저장 확인 문구 확인
가능하면 dialog 이벤트 처리기를 클릭 전에 준비
저장 클릭은 한 번 시작하고 완료 promise를 보관
짧고 제한된 대기 안에서 같은 탭의 dialog를 읽기
  알려진 저장 confirm이면 승인
  이어지는 정상 처리 alert도 확인하고 닫기
  새 문구·검증 오류·다른 행위면 읽고 그 내용에 맞게 처리
클릭의 성공/오류와 남은 dialog를 모두 회수
새 화면 또는 재진입으로 값이 저장됐는지 확인
```

- 첫 confirm만 처리하고 끝내면 두 번째 “정상적으로 처리되었습니다” 알림이 계속 제어를 막을 수 있다. 후속 alert까지 확인한다.
- 반복 횟수 증가를 해법으로 고정하지 않는다. 짧은 시간 제한과 실제 상태 변화로 판단한다.
- 클릭이 이미 완료됐다고 감시를 너무 일찍 끝내지 않는다. 반대로 진행 중 promise를 방치한 채 저장을 다시 누르지도 않는다. 현재 런타임의 취소·종료·재연결 방법을 따른다.
- 아무 confirm이나 자동 승인하는 전역 핸들러를 만들지 않는다. 저장 확인과 최종제출·지원취소·새 약관은 효과와 승인 범위가 다르다.

### 3. DOM 경로 실패 시 화면 경로로 전환한다

1. fresh DOM/접근성 상태에서 모달과 정확한 버튼을 다시 찾는다. `Node detached`, remount, 오래된 노드 번호는 새 조회로 복구한다.
2. DOM 계열 API만 실패하고 접근성 경로는 정상일 수 있다. `this._engines.keys is not a function` 같은 오류를 사이트 필수값 오류로 오진하지 않는다. 사용 가능한 다른 지원 UI 조회 경로를 쓴다.
3. 현재 스크린샷에 확인 버튼이 실제 보이면 그 스크린샷에 근거한 브라우저 컴퓨터 제어 좌표 클릭을 사용한다. 이전 화면의 좌표를 복붙하지 않는다. 클릭 후 다시 찍어 닫힘/다음 창을 확인한다.
4. 키보드 Enter는 현재 dialog의 포커스·기본 동작이 확인되고 그 동작이 승인된 경우에만 사용한다. 반응을 모르는 상태에서 Enter 연타하지 않는다.
5. 페이지 도구가 막히고 **현재 세션에서 네이티브 Computer Use가 제공·허용될 때** 실제 앱 창을 식별하고 새 화면/접근성 요소로 처리한다. 과거에는 Windows 제어로 저장 confirm과 후속 성공 alert를 각각 닫고 다음 단계로 이동했다.
6. 네이티브가 비활성화돼 있으면 PowerShell 마우스, 비공개 CDP, 임의 브라우저 내부 API로 우회하지 않는다. 가능한 브라우저 경로를 확인한 뒤 해결되지 않은 정확한 확인창 하나만 사용자에게 요청한다.

### 4. 오류 뒤 상태부터 확인한다

- timeout은 실패 확정이 아니다. 특히 제출 timeout 뒤 이미 제출 미리보기/완료 페이지로 이동한 사례가 있다. 마이페이지와 현재 화면을 읽은 후에만 재시도한다.
- 저장 성공 문구를 닫고 탭을 왕복하거나 미리보기로 값이 유지되는지 확인한다. confirm 승인만 성공했으면 `저장 미확인`이다.
- 스냅샷 한 번 실패를 연결 끊김으로 단정하지 않는다. 다른 지원 상태 조회·dialog·스크린샷으로 범위를 좁힌다. 실제 브라우저 세션/연결 실패가 반복되면 같은 조회만 반복하지 않고 로컬 작성·다른 허용된 회사로 진행한다.
- Chrome 탭 목록이나 화면 확인은 되지만 `getState`, 탭 claim, DOM snapshot 같은 제어 호출만 30초 안팎으로 반복 timeout이면 설치·native-host 고장으로 단정하지 않는다. 열린 탭과 로컬 작성본을 보존하고, 가능한 읽기 전용 탭 목록·스크린샷으로 상태를 기록한 뒤 사용자와 맞춰 Chrome 재시작/재연결을 시도한다. 복구 후에는 이전 탭 ID·노드 번호를 재사용하지 말고 URL·제목·화면부터 다시 식별한다.
- 사용자가 화면을 다시 열었다고 하면 과거 “마감됨/수정불가” 판단을 고집하지 않고 현재 경로를 새로 확인한다.
- 사용자 조작으로 보이는 예기치 않은 이동/행 삭제가 생기면 해당 탭 변경을 멈추고 상태와 작업 주체를 확인한다. 원인을 확인하기 전 사용자 조작이라고 단정하지 않는다.

## 날짜·자동완성·검증

- 사이트 placeholder와 실제 위젯을 따른다. 요구한 `YYYY-MM-DD`/`YYYY-MM` 대신 점 구분 날짜를 넣으면 초기화될 수 있다. 어떤 위젯은 `YYYY.MM` 입력과 별도 기간 팝업을 사용한다. 회사 이름만으로 형식을 고정하지 않는다.
- 달력 범위 위젯은 시작·종료 두 입력을 각각 확인하고 선택 확정/blur 후 바깥 요약값까지 읽는다. 직접 입력이 제한되면 제공 달력을 사용한다.
- 검색창에 학교·전공·회사명을 입력한 것은 선택 완료가 아니다. 비동기 결과가 나타난 뒤 실제 옵션을 선택하고 필드를 떠나도 값이 남는지 확인한다. 최초 무결과만 보고 임의의 유사 학교를 선택하지 않는다.
- 팝업이 안 보이면 새 탭/창 목록, dialog, 화면, 지원되는 프레임 조회를 확인한다. 주소검색 결과를 내부 DOM 값만 바꿔 위조하지 않는다.
- 공식 어학 연동에는 별도 로그인과 `성적확인 → 성적입력`이 필요할 수 있다. 등급을 타이핑한 것과 공식 성적 등록을 구분한다. 자동입력 값이 지워지면 현재 입력 방식·선택 확정을 점검한다.

## 파일 업로드

1. 현재 항목에서 허용하는 종류·실제 크기 제한·페이지/픽셀 규격과 선택한 원본을 확인한다.
2. 지원되는 `waitForEvent('filechooser')`를 **업로드 버튼 클릭 전** 등록한다.
3. 현재 화면의 실제 업로드 버튼을 누른다. DOM 클릭 실패 시 관측한 화면 좌표로 버튼을 클릭할 수 있다.
4. 반환된 chooser의 `setFiles()`에 확인한 절대 경로를 전달한다. 이 경로가 있으면 Windows 파일선택창 좌표 조작을 먼저 시도하지 않는다.
5. 파일명·미리보기·삭제/교체 버튼·업로드 완료를 확인한다. 사진 crop 확인 버튼과 페이지 저장은 별도 단계일 수 있다.
6. 파일chooser timeout 뒤 무작정 다시 누르지 말고 열린 창과 첨부 상태를 먼저 확인한다. 업로드 문제가 지속되면 사용 가능한 `chrome-file-upload-triage`를 읽는다.

변환은 원본을 보존한 업로드용 사본에 한다. 파일 크기 제한을 실제로 확인한 뒤 대응하고 사용자가 선택한 사진·증빙을 사용한다. 원문 논문 ZIP은 압축만으로 제한을 해결하지 못할 수 있다. 사이트가 요약본을 허용하면 제목·저자·초록 발췌를 명확히 표시해 제공하되 원문 필수 항목을 요약본으로 대체하지 않는다. 현재 적용되는 이미지/PDF 도구 지침을 따른다.

## 인증·승인·탭 유지

- Chrome과 내부 브라우저 로그인은 공유된다고 가정하지 않는다. 브라우저 전환 시 이유와 재로그인 필요를 알린다.
- 로그인·휴대전화 인증·CAPTCHA·새 암호 설정은 현재 도구 허용 범위에 따라 필요한 단계만 사용자에게 넘긴다. 비밀번호를 채팅/스킬에 적도록 요구하지 않는다.
- 인증메일 조회가 승인돼 있으면 대상 계정·서비스·최신 요청의 일치 여부를 확인한다. 관련 없는 수신자 주소를 보조 이메일로 임의 지정하지 않는다.
- 공통 채용 시스템은 한 로그인으로 여러 계열사를 처리할 수 있지만 지원서는 별개다. 탭은 사용자가 정한 묶음 크기로 준비하고, 도구가 지원하는 유지/handoff 기능을 사용한다. 작업 종료 시 임의로 닫지 않는다.
- 자동 승인 검토가 거절하면 우회하지 않는다. 거절된 행위와 도구가 제시한 사유, 필요한 사용자 조치만 짧게 설명한다. 일반 저장 확인을 별도 법적 동의처럼 취급해 불필요한 승인 흐름을 만들지 않는다.
