# Apply — 기업 사이트 지원

지원서 입력부터 저장·검토·승인된 제출까지 이어서 수행한다. 단순히 필수항목 오류가 없다는 이유로 완성으로 판단하지 않는다. 별도 이력란의 누락과 서버에 실제 반영된 상태를 확인한다.

## 호출과 범위

- 명시적 스킬 호출은 `$apply`. 사용자가 `/apply 현대차 지원해`라고 말한 경우에도 이 스킬의 작업 의도로 해석한다. 이 파일 생성만으로 앱의 네이티브 `/apply` 명령이 등록됐다고 주장하지 않는다.
- 최신 지시에서 대상 기업·직무·지망·브라우저와 `작성만 / 제출 직전 / 제출 / 수정 후 재제출` 범위를 잡는다. 기존 승인은 같은 범위에서 유지하며 이미 받은 확인을 반복 요구하지 않는다. 현재 도구의 추가 승인 요구가 있으면 그 구체적 요구만 따른다.
- 과거 문서의 “최종제출 금지”는 당시 작업 범위다. 이후 사용자의 “둘 다 제출해”, “다시 제출해”를 무시하는 영구 금지로 만들지 않는다. 반대로 스킬 호출 자체를 모든 기업·인재 Pool 가입·제출의 포괄적 허락으로 해석하지 않는다.
- 사용자가 중단·기업 제외·직접 입력을 요청하면 해당 조작과 예약된 후속 동작을 멈춘다. 최신 지시와 충돌하는 과거 진행계획을 재개하지 않는다.

## 1. 이전 작업과 현재 화면 확인

1. 특정 대화를 이어달라면 `list_threads`로 제목을 찾고 `read_thread`로 최신 결정, 사용자 정정, 완료·미완료를 확인한다. 이전 에이전트의 완료 주장도 현재 사이트에서 검증한다.
2. “크롬에 열어놨어”라면 현재 Chrome 탭 목록과 대상 탭의 URL·제목·화면부터 확인한다. 주변 UI에 내부 브라우저가 보인다는 이유로 브라우저를 바꾸지 않는다. 제어 도구는 현재 제공 문서를 읽고 지원되는 API만 사용한다.
3. 로그인 이후 리다이렉트·새 탭·세션 만료를 확인한다. 탭 번호와 접근성 노드 번호를 이전 실행에서 재사용하지 않는다. 도구가 지원하면 사용자에게 남길 채용 탭을 handoff/유지 대상으로 지정한다.
4. 새 직무를 고를 때는 현재 공식 채용공고의 실제 모집직무·담당업무·지원자격·입사 가능일·근무지·마감 시각·중복지원 제한을 확인한다. 일반 직무소개나 지난 채용의 문항을 현재 공고로 간주하지 않는다. 선택 근거와 미확인을 짧게 설명한다.

## 2. 원본과 전체 항목 대조

로그인만 요청받으면 프로필·자소서 전체를 읽지 않고 [로그인 및 효율적인 브라우저 제어](references/login-automation.md)를 따른다. 이 문서에 현재 사용자에게 허용된 로그인 방식과 DOM·Playwright 제어 우선순위가 있다. 지원서 작업에서도 로그인이 필요하면 먼저 읽는다.

프로필·이력·증빙을 다룰 때 [입력 사실과 누락 점검](references/application-data.md)을 읽는다.

- 자료 위치는 사용자가 지정한 개인 자료 폴더 또는 현재 작업 폴더에서 확인한다. 다른 사람의 프로필·경험·계정을 기본값으로 사용하지 않는다.
- 먼저 현재 자료 폴더의 `AGENTS.md` 등 작업 지침, 경험 우선순위, 지원자 프로필, 해당 기업의 최신 작성본, 업로드 파일 매핑을 확인한다. 파일명은 사용자 환경에서 찾고, 모든 사실을 스킬에 복제하지 않고 원본을 읽는다.
- 사용자 최신 정정과 증빙, 회사의 입력 정의를 함께 대조한다. 상충하면 날짜·값의 출처와 정정 시점을 기록하고 필요한 사실만 묻는다. 확인된 프로필 업데이트 권한이 있으면 원본과 해당 입력본을 함께 갱신한다.
- 지원서 **모든 탭과 반복 행**을 조사하여 다음 대조표를 만든다. 소규모 작업은 기존 진행기록에 넣으면 된다.

| 사이트 항목 | 적용할 사실·원본 | 화면 입력값 | 상태·이유 |
|---|---|---|---|
| 예: 해외 경험 | 교환학생 전체 기간과 설명 | 저장 후 다시 읽은 값 | 검증 완료 / 미입력 / 사실 확인 필요 / 비해당(이유) / 입력란 없음 |

- 필수 검증과 별개로 원본에 있는 해외 경험, 경력, 논문, 수상, 교육, 장학·활동 이력을 빠짐없이 점검한다. 자소서에 이미 언급했어도 별도 이력란을 생략하지 않는다. 분류가 맞지 않으면 적합한 다른 이력란을 찾되 자소서에 억지로 추가하지 않는다.

## 3. 입력과 저장

- 현재 회사의 실제 문항·하위 요구·분량을 확보한 뒤 기존 초안을 맞춘다. 자소서 작성·수정에는 사용 가능한 `tailored-jasoseo`를 적용한다. 참조 자료나 검증 스크립트가 없으면 가능한 대체 검증을 하고 한계를 밝힌다.
- 현재 사용자가 정한 경험 우선순위를 적용하고 문항별 사건을 구분한다. 논문 채택을 발표·출판 완료로, 제1저자를 단독저자로, 지원 업무를 전체 책임으로 확대하지 않는다.
- 한 페이지를 완성한 뒤 저장한다. 도중 큰 입력 손실 위험이 있으면 필요한 중간 저장을 한다. 날짜·자동완성·체크박스·파일은 입력 직후 화면 값과 선택 확정을 확인한다.
- 확인창, 무반응, 지연, 업로드 실패가 나오면 즉시 [브라우저 복구 절차](references/browser-recovery.md)를 읽고 원인에 맞는 지원 경로로 처리한다. 곧바로 사용자에게 “확인 눌러주세요”를 반복하지 않는다.
- 저장 성공 알림을 처리한 다음 다른 단계에서 돌아오거나 미리보기로 재조회하여 서버 반영을 확인한다. 실패한 클릭이 이미 실행됐을 수 있으므로 재시도 전에 상태부터 읽는다.

## 4. 제출·수정 검증

1. 제출 직전 실제 직무·지망·근무지, 학력·전공성적, 경력 시제, 해외 기간, 모든 적용 가능한 이력, 첨부, 각 답변과 글자/byte 제한을 대조표로 확인한다. 미해결된 필수 사실은 만들어 채우지 않는다.
2. 현재 범위가 제출을 허용하면 완료된 검토를 바탕으로 제출한다. 작성만 요청했거나 수정 불가 회사는 제출 직전까지만 하라는 지시가 유효하면 그 경계에서 멈춘다.
3. 제출 버튼 뒤 확인창과 결과 화면을 처리한다. 마이페이지의 `지원완료/제출완료`, 제출일시·접수번호 또는 이에 준하는 명시적 사이트 증거를 확인한다. 오류 없음이나 버튼 클릭만으로 완료라고 하지 않는다.
4. 수정 요청은 실제 사이트 수정 경로와 마감 상태를 확인한다. 수정본 저장 후 재제출이 필요한지 확인하고, 수정된 필드와 제출 상태를 다시 읽는다. 원본 파일만 고쳤거나 임시저장만 됐으면 그 상태로 보고한다.
5. 기존 제출본 수정이 막혔다면 사실과 정정안을 로컬에 남긴다. 사용자 요청 없이 지원 취소·새 지원서 중복 생성·채용담당자 연락을 하지 않는다.

## 기록과 전달

기존 `_workspace/application_YYYYMMDD/` 또는 해당 기업 검증 기록을 활용한다. 기업·직무·지망, 확인한 공고와 시각, 원본 변경, 입력/저장/제출 상태, 누락 사유, 미해결 사실, 최종 화면 근거를 남긴다. 실제 본문·분량도 재사용할 수 있게 저장한다. 암호·인증코드·세션 토큰을 스킬이나 진행기록에 복사하지 않는다.

진행기록·현황표처럼 한글 UI 문구가 긴 파일을 PowerShell로 갱신할 때는 UTF-8 here-string이나 구조화된 파일 쓰기를 사용한다. 따옴표가 섞인 제출 완료 문구를 한 줄 `-replace` 문자열에 직접 넣으면 파서 오류가 날 수 있으므로, 실패하면 상태를 재확인한 뒤 전체 블록 쓰기나 안전한 스크립트로 전환한다.

최종 답변은 회사별 완료 상태와 남은 조치만 간단히 적는다. 사용자가 제출한 것을 확인했다면 “사이트에서 제출 완료 확인”이라고 구분한다. 필요한 사용자 작업은 해당 로그인·인증·사실 하나로 좁히고 다른 허용된 작업은 계속한다.

의사결정 회귀 점검에는 [검토 시나리오](references/review-scenarios.md)를 사용한다. 실제 지원서를 테스트 제출하지 않는다.
